## 死锁问题概述

### 死锁的正式定义
- A set of processes is deadlocked if each process
in the set is waiting for an event that only another
process in the set can cause.
 Assume that processes have only a single
thread.
  - Assume that there are no interrupts possible to
wake up a blocked process.
  - Usually the event is release of a currently held
resource.
  - The number of processes and the number and
kind of resources possessed and requested are
unimportant.

### 死锁的4个充分必要条件
- 互斥条件
- 保留和等待条件
- 无抢占条件
- 循环等待条件

## 对死锁的处理方式1：Ostrich Algorithm
鸵鸟算法是一种处理死锁的方式，核心是利用重启解决死锁问题，对死锁采取 “忽略” 态度，不主动预防或检测。

- 死锁概率与时间成本的考量
  - 对于多数系统，死锁是小概率事件（如用户误操作、极端资源竞争），为罕见事件投入高成本的处理算法并不划算。
- 风险与效率的权衡
  - 接受死锁可能发生的风险，以换取系统在大多数无死锁时间的高效运行。
- 实际系统应用
  - Unix/Windows系统用这个算法管理一些 **更加复杂的依赖关系**


## 对待死锁的方式2: 定期检测和恢复  
### 核心策略  
1. **允许系统进入死锁状态**：不提前预防或避免死锁，而是在死锁发生后主动处理。  
2. **定期运行死锁检测算法**：通过周期性检查系统状态，识别是否存在死锁。  
3. **检测到死锁后运行死锁恢复算法**：通过抢占资源、终止进程等方式打破死锁。  
4. **典型应用场景**：数据库系统（需保证事务可靠性，允许短暂死锁后恢复）。  


### 死锁的检测  
#### 1. 单资源类型（Single Source Per Type）  
- **检测对象**：每种资源仅有一个实例（如打印机、磁带驱动器）。  
- **检测方法**：  
  - **资源分配图法**：构建有向图，节点分为进程（P）和资源（R），边表示“进程请求资源”或“资源分配给进程”。  
  - **算法步骤**（深度优先搜索DFS）：  
    1. 对每个进程节点作为起点，初始化遍历列表 $ L $ 和未标记边集合。  
    2. 沿请求边深度遍历，标记已访问的边，若同一进程节点在 $ L $ 中重复出现，形成环（死锁）；若遍历完所有边无环，则无死锁。  
  - **判定条件**：图中存在环 ⇒ 死锁发生；无环 ⇒ 系统安全。

#### 2. 多资源类型（Multisource Each Type）  
- **检测对象**：每种资源有多个实例（如CPU核心、内存块）。  
- **检测方法**：  
  - **矩阵-based算法**：使用以下数据结构描述系统状态：  
    - $ E $：现有资源向量（总资源数）。  
    - $ A $：可用资源向量（未分配资源数）。  
    - $ C $：当前分配矩阵（进程已占用的资源数）。  
    - $ R $：请求矩阵（进程申请的资源数）。  
  - **算法步骤**：  
    1. 初始化所有进程为“未标记”，寻找满足 $R_i \leq A$  的进程 $ P_i $（请求可被满足）。  
    2. 若找到 $ P_i $，将 $ C_i $ 释放到 $ A $ 中，标记 $ P_i $ 为“可完成”，重复步骤1。  
    3. 若无法找到可完成的进程，未标记的进程构成死锁集合。  
  - **判定条件**：存在未标记进程 ⇒ 死锁发生；所有进程可标记 ⇒ 系统安全。  


### 检测算法对比  
| **场景**     | **单资源类型**              | **多资源类型**                     |
| ------------ | --------------------------- | ---------------------------------- |
| **核心思想** | 检测资源分配图中的环（DFS） | 模拟资源分配序列（银行家算法变种） |
| **数据结构** | 有向图（进程-资源边）       | 矩阵（分配、请求、可用资源）       |
| **复杂度**   | $ O(N+E) $（图节点和边数）  | $ O(N×M) $（进程数×资源类型数）    |
| **适用场景** | 专用设备、独占资源          | 共享资源池（如内存、CPU核心）      |

通过定期执行上述检测算法，系统可在死锁发生后快速定位，并触发恢复机制（如终止死锁进程、回滚事务），平衡了资源利用率与系统可靠性，是数据库等强一致性系统的常用策略。

## 避免死锁(Avoid Deadlock)

### 引入1: 最大资源需求表格

考虑如下表格：
- ![alt text](images//image-2.png)

- Max那一栏存储了每个进程对每类资源的**声明最大需求**。这是进程给出的一个**保证**，保证 实际最大资源需求 $\leq $ 声明的最大资源需求。 $实际最大 \not ={理论最大}$
- Available 一栏记录了系统实际可用的资源。

### 引入2：安全状态与非安全状态与死锁状态

- 安全状态: 
  - 若每个进程 `实际最大需要资源 == 声明最大资源` ，**使用银行家算法**能够找到一个进程执行序列 $\langle P1,\dots P_n \rangle$ 使得每个进程都能够顺利执行。 
  - 推论：若部分或者全部进程 实际完成任务需要请求的资源 $\leq$ 声明最大资源，则存在至少一个执行序列 $\langle P1,\dots P_n \rangle$ 使得每个进程能够顺利执行。

- 非安全状态：
  - 安全状态以系统全部状态为全集下的补集。
  - 非安全状态并不一定导致死锁。原因：每个进程可能实际上不会请求如它们声明的那样多的资源；每个进程也可能会中途突然释放一会某些资源，使得释放后的可用资源能够满足进程运行的需要。

### 问题: 如何判定一个资源分配操作是否会使系统进入不安全状态

- 使用类似银行家算法的安全性检测算法。
- 算法步骤：
  - 执行当前分配，如果成功分配则继续，不成功就标记这次分配为 Unsafe。
  - 更新 Alloc 矩阵, Need 矩阵 和 Available 向量
  - 轮询 Need Matrix 直到所有的进程都被标记为已完成。
    - 如果找到 $N_i <= Available$,则分配资源给$P_i$,标记$P_i$ 为已完成。
    - 否则退出轮询，将这次分配标记为 unSafe。
    - 将完成的资源释放，更新Alloc,Available，Need 矩阵。
  - 将这次分配标记为 Safe.

### 算法2：银行家算法

- 并发性和安全性的Trade of
- 不是非常实用
  - 进程很少能够知道其最大资源需求。
  - 进程的数量不是固定的
  - 被认为可用的资源可能会突然消失。
- 基本思路：
  - 始终保持在 Safe State
- 算法描述：
  - 从优先级队列中取出一个进程，执行其分配操作。
  - 检查分配后状态是否处于Safe
    - 是，继续处理下次分配请求
    - 不是，推迟这次分配，将进程加回优先级队列中。
